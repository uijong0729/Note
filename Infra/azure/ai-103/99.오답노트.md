# D1: Azureで生成型 AI アプリを開発する

## モデルとプロンプト
### 温度
- 温度を下げると、応答のランダム性が減り、同じ入力に対する出力の再現性・一貫性が高まります。
- 出力の一貫性を下げたり上げたりするために、最初に調整すべきモデル パラメーター
### top_p
- 確率上位の語彙に絞って出力をサンプリングする推論パラメータ
- 創造性とランダム性を調整したいと考えている場合、応答の多様性を制御する
### ペナルティ
- 頻度ペナルティ: 同一トークンの繰り返しを抑える調整
- 存在ペナルティ: 新しい話題の出現を促す調整
### マルチパートユーザーメッセージ
- テキストと画像を1つのユーザーメッセージにまとめて送信できる形式

## Foundry Tools と評価
### REST API
- Ocp-Apim-Subscription-Key：リクエストにキーを付与するために使用するHTTPヘッダー
### 評価機能
- 評価には、入力と評価基準を含むテストデータセットを先ず用意する必要がある。
- 関連性(relevance)・根拠性(groundedness)などの評価メトリックを選び、データセットに対して評価を実行することで、応答品質を体系的に測定できる。
- グラウンデッドネス（groundedness）
    - 応答が提供されたソースの内容に基づいているかを評価するメトリック
    - でっち上げ（ハルシネーション）の検出に直結する
    - エージェントの命令で取得（グラウンディング）動作を指定することが重要な理由
        - 命令で「取得した情報に基づいて回答する」ことを明示しないと、モデルは接続済みナレッジ ソースを使わず訓練データの一般知識から回答しがちになる。
        - 結果として検証不能で出典のない応答になる。
- モデルのドリフト(drift：漂流)
    - ユーザーが入力する内容の傾向が時間とともに変わることで、デプロイ当初より応答の精度や関連性が落ちていく現象
- 関連性 : モデルの応答が、利用者の質問の意図にどれだけ的確に対応できているかを測りたい場合、用いるべき評価メトリック

## Microsoft Foundry ポータルとクォータ
- 生成AIアプリの開発で、複数の基盤モデルをカタログから比較・選択し、デプロイやプロンプト テスト、評価までを 1 つの統合環境
- クォータ：Foundryプロジェクトのリソース使用量の上限を定義する仕組み

## 認証とセキュリティ
### マネージド ID
- Microsoft Entra ID が発行・管理する ID で、シークレットをコードに保存せずトークンベースでリソースにアクセスでき、キーのローテーション運用も不要
### Shared Access Signature
- 有効期限付きトークン文字列を発行する仕組みで、依然として資格情報の生成・配布・更新が必要

## OpenAI API とモデル推論
### OpenAI API
- responses.create()
    - OpenAI 互換クライアントを取得してから実行
    - Responsesを用いて応答を生成する際に呼び出すメソッド
### モデル推論 API
- デプロイ済みモデルにプロンプトを送り、応答のストリーミングや関数呼び出しを統合するためにアプリコードから直接呼び出すインターフェイス

## デプロイオプション
### 標準デプロイ
- 容量予約が不要で、処理したトークン量に応じた従量課金
- トラフィック・リージョン分散を必要としないシナリオに合致
### プロビジョニング済みスループットデプロイ(Provisioned Throughput Deployment)
- 定額で、容量を事前予約する方式
- Provisioned Throughput : 準備された処理量
### バッチデプロイ
- 大量リクエストを非同期でまとめて処理する方式
- 対話型のリアルタイム利用はできない

# D2: Azureでの AI エージェントの開発

## エージェントの設計とオーケストレーション
### 操作の事後追跡・規制対応
- トレース ログと実績メタデータ、および承認ワークフローを用いた監査により、エージェントの各操作の時刻・内容・根拠を後から追跡できます
### ツール
- OpenAPI 仕様ツール
    - OpenAPI定義を持つWebサービスの呼び出し
- tool capability(ツール機能)の種類
    - web_search : Web検索
    - code_interpreter : Pythonコードの実行
    - file_search : アップロード文書からの回答用ツール
### オーケストレーションパターン
- 複数のエージェントやサービスを調整し、連携させる方法や設計のパターン
- **引き渡し(Responsibility Handover)**
    - 最初に応対した一次受けエージェントが、問い合わせ内容に応じて、状況の変化に合わせて適切な専門エージェントへ責任そのものを動的に移譲（いじょう）するパターン
- **逐次（Sequential）**
    - エージェントを事前に定義した順序で順番に実行するパターン
    - 依存関係があるなら逐次
- **コンカレント（並行、Concurrent）**
    - 複数のエージェントを並列に実行し、結果を統合するパターン
    - 応答時間を最短化
    - 各領域に依存関係がない
- **グループチャット（Group Chat）or Collaboration**
    - 複数のエージェントが同じタスクを協力して行うパターン

## Microsoft 365 Agents Toolkit
- カスタムSSO・カスタムミドルウェア・複数環境へのデプロイなど、Teams向けエージェントの高度なカスタマイズと環境管理に使う

## エージェント開発 SDK
### Python SDK
- AIProjectClient
    - PythonアプリからFoundryプロジェクトへ接続し、ネイティブなプロジェクト操作を行うために使用するクライアントクラス
    - `from azure.ai.projects import AIProjectClient`
- get_openai_client()
    - AIProjectClient から OpenAI 互換クライアントを取得するメソッド
### Microsoft Agent Framework
- AzureAIAgentClient
    - Azure AI バックエンドに接続するためのクライアント
    - from agent_framework.azure import で取得する

## 会話スレッド
- ユーザーの入力とモデルの応答をまとめて保持する会話の単位
- 同じスレッドを参照すれば、エージェントが過去の文脈を踏まえた応答を生成

## MCP(Model Context Protocol)
- アプリケーションと、AIモデル間でやり取りするためのプロトコル
- ClientSession
    - MCPサーバーに接続するクライアントセッション
    - list_tools() : 接続先サーバーから、呼び出せるツールの一覧を取得

## Work IQ
- **Microsoft 365** のコンテキスト インテリジェンス層
- 組織の働き方の文脈をエージェントに提供する

# D4: Azure で自然言語ソリューションを開発する

## Azure AI Translator
### Document Translation
- 書式（レイアウトや見出し構造）を保ったまま Word や PDF のファイルそのものを丸ごと別言語に翻訳
### transliterate（表記変換）
- 同一言語の内容を別の文字体系（スクリプト）に変換する
- 日本語の住所表記を、発音を保ったままローマ字（ラテン文字）の表記に変換

## Azure Speech SDK
### speech_synthesis_voice_name
- プロパティに音声（ボイス）名を設定することで、合成に使用する音声を指定する
- カスタム音声モデルを含め、合成音声の指定はこのプロパティで行う
### SpeechTranslationConfig
- 音声翻訳の構成クラス
- add_target_languageで翻訳先言語を指定します。
- 同時通訳ワークフローに使用します。
### speak_text_async()
- 与えた文字列を実際に音声へ合成するために呼び出すメソッド

## 自然言語ソリューション
- エンティティ・トピック・要約の抽出と構造化 JSON 出力
    - 生成プロンプトで抽出対象とトピックを指示する
    - 出力を構造化 JSON 形式で返すよう指示する

## Azure Language MCP サーバー
- テキスト分析の機能をMCPツールとして公開し、エージェントから名前付きエンティティの抽出などを呼び出せるようにする

# D5: ナレッジ マイニングと情報抽出

## ドキュメント理解とコンテンツ理解
### Azure Content Understanding
- プロジェクト作成の GUI ツール
- ドキュメント理解・コンテンツ理解を支援する統合ツール
- 標準モード：単一ファイル
- Proモード：複数ファイルの同時処理と多段推論
### 情報抽出
- Content Understanding：analyzeを呼び出し（すぐに解析結果を返さず）、結果を取得するにはOperation-Locationをポーリング(polling)して取得

## Azure AI Search
### リソースの役割
- スキルセット : AIエンリッチ処理の手順定義
- データソース : 取り込み元
- インデクサー : 両者を結ぶ実行単位
### シノニムマップ（Synonym Map）
- 異なる語句や表現が同じ意味を持つことを定義するリソース
### セマンティック検索
- 検索クエリの意味を理解して、より関連性の高い検索結果を返す検索機能
### ベクター検索
- 検索クエリをベクトルに変換し、ベクトル空間上で類似度の高いドキュメントを検索する機能
### ハイブリッド検索
- キーワード（全文）検索とベクター（意味的）検索を組み合わせ、両方の長所を活かして文書を取得
- キーワードの一致だけでなく、語句の意味的な近さでも文書を取得する検索方法

## Azure AI Search スキルセット（skillset）
- AIスキルによる「エンリッチ処理」の手順を定義するリソース
    - エンリッチ処理 : データやドキュメントから意味のある情報を抽出してデータを強化する過程
- OCR（Optical Character Recognition）やエンティティ抽出などの強化ステップをまとめる
- スキルの出力を後続のスキルや、インデックスのフィールドへ正しく渡すために、スキル定義で指定する必要がある要素
    - 出力をマッピングする対象の名前
    - 出力の名前

## Foundry IQ
- Azure AI Search 上に構築する集中型ナレッジ層
- エージェント向けのナレッジ層として、エージェンティック検索・RAG に用いる
- エージェンティック検索：エージェントがユーザーの質問に応じて、関連する情報を検索して取得する機能
- RAG（Retrieval-Augmented Generation、取得拡張生成）
    - 関連情報を検索して取得し、生成モデルの応答に組み込む手法
    - 頻繁更新データの反映

## 埋め込みモデル（embedding model）
- テキストをベクトルに変換するモデル

## カスタム分類子の訓練
- 入力データを独自のカテゴリに分類するモデル
- 最低 2クラス、各クラスにつき、5サンプル以上

## 出力スキーマ
- 指定して構造化出力を有効にすると、決まったキーを持つ形式で応答が返り、後続プログラムが確実に解析できる。
